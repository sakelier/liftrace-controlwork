## 3. 当前任务链能力

正式入口是：

```text
navigation_search_delivery_vcl06.launch
  -> random field / planner anchor / map / control_ready 启动屏障
  -> Mission Manager 覆盖搜索与候选权重队列
  -> Planner Bridge 单一 /fastplanner/goal 发布者
  -> 同一 stable ID 的 APPROACH / ALIGN / RELEASE / RECOVERY 事务
  -> 三次投递成功
  -> 11 点 post_delivery_route
  -> Wall_15 -> Wall_20 -> Wall_22
  -> final landing_h_clone
  -> fresh H alignment -> PX4 AUTO.LAND
  -> ON_GROUND + disarmed
```

任务 profile 固定为 `r2026`，暂不把 tank 放入比赛任务队列：

```text
red_cross=10.0, panzer=2.5, bridge=2.0, pillbox=1.5, tent=1.0
```

正式 VCL06 不再使用旧临时 `coverage_search_manager` 的 `interrupt.min_weight`。唯一策略来源是
`competition_profiles.yaml` 的 `r2026.interrupt_top_k=3`，因此有效最低权重为 `2.0`：
`red_cross`、`panzer`、`bridge` 都会立即中断搜索，`pillbox`、`tent` 只作为覆盖完成后的后备候选。
正式随机场生成四类标准靶和一个随机红十字；tank 可保留诊断检测，但不得成为 selected/投递目标。
r9 已同时实证 panzer 和 red_cross 都产生 `high_weight_search_interrupt`，不存在“正式链只有红十字
可中断”的行为。

三投后的路线 revision 为 `toudi3-random-three-door-h-r1`：

- Wall_15：从南向北，洞口高度 `0.50..1.30 m`；
- Wall_20：从西向东；
- Wall_22：从西向东；
- 最终 H：`camera_init=(3.274292, 8.057220)`，捕获高度 `0.75 m`。

任务在 420 秒触发强制返航，为走廊和降落预留 180 秒。安全异常（释放结果不确定、恢复失败、强制
返航）会绕开计分走廊，直接走最短返航，不为过门分扩大飞行风险。

## 7. 推荐的双仓联合方式

视觉与导航仓没有共同历史，不再做本地 Git merge。使用两个已同步的 feature 分支组成 ROS overlay：

```text

              feat/vcl06-local-full-mission@34ce0c3
导航任务实现：/home/xhj/liftrace-controlwork-worktrees/vcl06-local-full-mission
              sakelier/liftrace-controlwork:feat/vcl06-local-full-mission
```

导航仓自己的 `vision_ws/src/uav_vision` 只保证消息合同可生成，其 `phase_d.launch` 仍是旧运行实现，
不接受正式链要求的 `class_profile`、`require_alignment_context`。因此单独使用导航仓
`uav_vision` 解析完整入口会以 unused args 失败，这是明确依赖提示，不能通过删参数绕过。联合运行时
必须最后 source 视觉工作区，使 `rospack find uav_vision` 指向视觉冻结工作树；同时确认
`phase_d.launch` 保留第 4 节全部接口。

旧临时 `coverage_search_manager.py` 与 `coverage_policy.py` 均未进入导航分支；历史文件名
`coverage_toudi3_random.yaml` 只保留随机场生成几何，旧 `interrupt.min_weight` 等无人读取的策略段
已删除。正式搜索/中断/投递策略只在 `vcl06_random_field_runtime.yaml` 和 MissionCore 中维护。

导航上游 PR #1～#6 已全部合入。后继导航成果曾以跨 fork PR #8 提交，但因 121 个文件和
`legacy_baseline` 快照导致审阅面过大，现按 owner 要求关闭并改在上游同名 feature 分支持续整理。
在完整 Gate PASS 前不由 agent 合并 `main` 或打 tag；后续应按消息合同、任务/执行链、旧控制最小
补丁、仿真资产与测试拆成可独立审阅的小 PR/Gate。

## 9. 完整 Gate 的唯一 PASS 条件

必须生成 `logs/<run>/gate_status.json` 且 `status=PASS`，同时满足：

- start Gate 只成功一次，且发生在 `control_ready=true` 后；
- PlannerStatus 无业务序列倒退、重放或未知事件；
- 三次成功投递为同一 stable ID 的完整事务，无错槽、重复释放或超时证据；
- 11 个 post-delivery 目标严格按 revision/顺序执行；
- Wall_15、Wall_20、Wall_22 按规定方向和洞口范围通过；
- LAND 后观察到新鲜 H 地图点和 `align_mode=landing`；
- 最终 `ON_GROUND` 且 `armed=false`；
- 全程零碰撞、零越界、高度不超过 4 m，总任务不超过 600 秒。

如果 manager 先 COMPLETE 而落地/解锁证据未齐，assertion 会继续 WAITING 到任务 wall timeout；不得
手工把 COMPLETE 改写成 PASS。
